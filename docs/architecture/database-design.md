# Database Design Rules

> Status: Phase 0 draft · PostgreSQL 18 · Prisma ORM 7.x (ADR-0002) · Tenant isolation per ADR-0004. Verified 2026-10-19.

## 1. Keys and identifiers

- **Primary keys: UUIDv7** (time-ordered, so B-tree inserts stay local and rows sort by creation time). Generated by the database (`DEFAULT uuidv7()`, built in from PostgreSQL 18) or by the application where an id is needed before insert (idempotency).
- Human-readable codes (`CBR-P-00123` for properties, lead numbers) are separate columns, unique per org, generated from per-org sequences held in a `counter` table updated under row lock.
- Never expose sequential integers in URLs.

## 2. Tenant isolation

1. Every tenant-owned table: `org_id uuid NOT NULL REFERENCES organization(id)`.
2. **Composite foreign keys** on tenant relationships where practical, e.g. `FOREIGN KEY (org_id, lead_id) REFERENCES lead(org_id, id)`. This makes it structurally impossible to link a task in org A to a lead in org B. Each tenant table gets `UNIQUE (org_id, id)` to support this.
3. **Row-level security** on every tenant table:
   ```sql
   ALTER TABLE lead ENABLE ROW LEVEL SECURITY;
   ALTER TABLE lead FORCE ROW LEVEL SECURITY;
   CREATE POLICY tenant_isolation ON lead
     USING (org_id = current_setting('app.org_id', true)::uuid)
     WITH CHECK (org_id = current_setting('app.org_id', true)::uuid);
   ```
   (Illustrative policy shape.) If the setting is missing, `current_setting(..., true)` returns NULL and the policy matches nothing, so access **fails closed**.
   **Spike S1 finding:** after a transaction-local `set_config` ends, PostgreSQL reports the setting as `''` (not NULL) on that connection, and `''::uuid` raises an error. The proven policy shape is therefore `org_id = (SELECT app.current_org_id())` with `app.current_org_id()` = `nullif(current_setting('app.org_id', true), '')::uuid`. The scalar sub-select is evaluated once per query and keeps index use ([S1 report](spikes/S1-report.md)).
4. **Database roles:**
   - `crm_migrator` owns the schema and runs migrations.
   - `crm_app` is used by web and worker: DML only, not the owner, no `BYPASSRLS`.
   - `crm_platform` is used by platform-admin queries over the `organization` table and platform metrics views. It has no grants on tenant PII tables.
   - `crm_auth` is used **only** by the authentication library (Better Auth) for its own tables: `user`, `session`, `account`, `verification`, `two_factor`, `organization`, `organization_membership`, `invitation`. It has no grants on business tables. Approved by the owner as D2 (2026-10-19); see [prisma/README.md](../../prisma/README.md) for the exact grants.
   - `crm_definer` (NOLOGIN) owns the pre-tenant `SECURITY DEFINER` functions and has column-level SELECT grants plus its own `definer_lookup` policies (point 9). No role used by the app has `BYPASSRLS`.
   - `crm_readonly_reporting` is reserved for a future read replica.
5. The app sets the tenant **per transaction** with `SELECT set_config('app.org_id', $1, true)` (transaction-local, so it is safe with pooled connections). The `withTenant()` helper is the only way to obtain a tenant-capable Prisma transaction client. A lint rule bans importing the raw client outside `src/platform/db`.
6. Own/team **scope** predicates are applied in repositories, not RLS. Team membership changes too often, and the predicates need joins that are easier to test in application code. RLS guards the org boundary, which is the catastrophic-failure boundary.
7. A CI test connects as `crm_app` without setting `app.org_id` and asserts that every tenant table returns zero rows.
8. **Coverage rule:** *every* table holding organisation-owned data carries `org_id` and an RLS policy, **including child tables** (`import_row`, `site_visit_property`, `task_reminder`, `escalation`, `brokerage_payment`, `lead_activity`, `communication_event`, `outbox_event`…). Child rows never rely on the parent's policy. A catalog query in CI lists tables with an `org_id` column but without `relrowsecurity AND relforcerowsecurity`, and fails if any appear.
9. **Pre-tenant lookups** (needed before an org context exists) never relax tenant policies. They go through narrow `SECURITY DEFINER` functions, owned by a dedicated non-login role, with a fixed `search_path`, returning the minimum columns:
   - `auth_memberships_for_user(user_id)` → `(org_id, membership_id, role_code, status)`: session → active org resolution.
   - `resolve_webhook_connection(token_hash)` → `(org_id, connection_id, provider)`: webhook routing.
   - `resolve_share_token(token_hash)` → `(org_id, share_id, expires_at)`: public property share pages.
   - `resolve_invitation(token_hash)` → `(org_id, invitation_id, email, status, expires_at)`.
   Each function has its own negative tests and is listed in `prisma/README.md`.
10. **Platform-scoped tables** (`organization`, `user`, auth/session tables, platform part of `audit_log` where `org_id IS NULL`) have explicit policies:
    - Users read only their own `user` row via `app.user_id`.
    - `organization` rows are visible to `crm_app` only for `id = app.org_id`.
    - `audit_log` rows with `org_id IS NULL` are visible only to `crm_platform`.
11. The tenant spike (S1) must prove points 1–10 before Phase 1 builds further modules ([PHASE-0-FINAL-REVIEW.md §7](../PHASE-0-FINAL-REVIEW.md)).

## 3. Integrity

- Foreign keys everywhere, with `ON DELETE RESTRICT` by default. Cascades only for pure child rows (e.g. `import_row` when an import is purged by retention).
- Enum-like columns: PostgreSQL enums for stable platform-defined sets (stage, outcome group). Text + CHECK or lookup tables for org-configurable lists (lost reasons, sources).
- Key constraints:
  - partial unique open-lead phone;
  - exclusion constraint for assignment spells (`btree_gist`);
  - exclusion constraint for overlapping leave;
  - unique provider event ids;
  - unique `(import_job_id, row_number)`;
  - unique idempotency keys.
- `version int` columns for optimistic locking on Lead, Task, SiteVisit, Deal, Property.
- Reopening a Lost lead fails if a newer open lead with the same phone exists. The user is offered a merge instead (lead-lifecycle §5).

## 4. Soft deletion, archiving, erasure

| Mechanism | Used for | Behaviour |
|---|---|---|
| `archived_at` | Leads, properties, scripts, teams | Hidden from default lists, fully restorable, still in reports |
| `deleted_at` (tombstone) | Leads created by mistake, merged leads (`merged_into_lead_id`) | Excluded from reports. Restorable by admin for 30 days, then purged by the retention job |
| Status-based close | Tasks (CANCELLED), deals (CANCELLED), memberships (DEACTIVATED) | Never deleted; history matters |
| **Erasure (anonymisation)** | Data-principal requests, org termination | PII columns overwritten/nulled, raw payloads/notes deleted, files deleted. Non-PII facts (stage milestones, counts) retained for aggregate integrity. An audit entry is kept, without the PII |
| Hard delete | Ephemeral rows (outbox, expired sessions, old notifications, import rows after retention) | Scheduled purge |

Append-only tables (AuditLog, LeadStageHistory, LeadAssignmentHistory, CommunicationEvent, ConsentRecord, BrokeragePayment) are never updated (except `ended_at` on assignment spells) and never deleted except by retention/erasure jobs running as `crm_migrator`-level maintenance roles.

## 5. Time

- All instants are `timestamptz`, stored in UTC. The app server runs with `TZ=UTC`.
- Calendar dates without time (leave dates, brokerage `expected_on`) use `date`.
- Org time zone (`Asia/Kolkata` default) converts "today", working hours and KPI day boundaries. The conversion is done in SQL (`AT TIME ZONE org.time_zone`) for aggregates.
- Display formatting happens in the presentation layer using the org/user locale (`en-IN`: `19 Oct 2026, 3:45 pm`).

## 6. Money

- `numeric(15,2)` plus `currency char(3)` (default `INR`). Max ₹9,999,999,999,999.99.
- Prisma `Decimal` in code. Arithmetic uses decimal.js (bundled with Prisma's Decimal). **No JS `number` for money.** Percentages are `numeric(6,3)`.
- Display: Indian digit grouping (₹1,25,00,000) and the "Cr/L" shorthand in UI. Parsing "1.2 Cr" and "85 L" is supported in imports.
- Lead budget fields use the same type. Rents are monthly.

## 7. Phone numbers and contact data

- Stored as E.164 text (`+919876543210`), validated with libphonenumber-js (default region IN). The raw input is kept separately.
- `phone_last10` generated column for suffix search.
- Email is `citext`.
- PII columns are listed in a registry (`pii.ts`) used by the logger redactor, the audit diff redactor, the export watermarking and the erasure job.

## 8. Pagination, sorting, querying

- **Keyset (cursor) pagination** for all lists: `ORDER BY <sort_col>, id` with an opaque cursor of the last row's values. Offset pagination only for small admin tables (< 1,000 rows).
- Max page size 200 (NFR-010). Totals use `count(*)` only when cheap (filtered by an indexed predicate) or approximate (`EXPLAIN`-estimated / "1,000+") otherwise.
- **Explicit `select`** projections in every repository query. No `include` cascades in list endpoints, which avoids N+1 and over-fetching.
- Batch loading for related data (`WHERE id = ANY($1)`), never per-row queries in loops.
- Every new list filter needs an index review (an `EXPLAIN ANALYZE` on a seeded 250k-lead dataset attached to the PR).
- Statement timeout for the app role: 10 s. Reporting role: 30 s.

## 9. Indexing baseline

The indexes listed in domain-model.md. Principles:
- Lead the composite with `org_id`.
- Use partial indexes for "open" subsets (open tasks, open leads).
- Use `pg_trgm` GIN for name search.
- Revisit with `pg_stat_statements` at the end of each phase.

## 10. Concurrency

- Assignment: optimistic lock on `lead.version` plus the assignment-spell exclusion constraint. Round-robin uses `SELECT … FOR UPDATE` on the `team_assignment_state` row, so concurrent imports get distinct, fair assignees.
- Import dedup: unique index plus `INSERT … ON CONFLICT DO NOTHING RETURNING`. Rows that hit a conflict are re-processed as attach-to-existing.
- Webhooks: `INSERT … ON CONFLICT (provider, external_event_id) DO NOTHING`. Only the inserting request enqueues processing.
- Counter tables are locked row-wise and kept short.

## 11. Migrations

- Prisma Migrate generates SQL migration files that are reviewed in PRs. RLS policies, exclusion constraints, partial indexes and triggers are written as raw SQL in the migration (Prisma schema cannot express them all). They are documented in `prisma/README.md`.
- **Expand → migrate → contract** for breaking changes. Never drop or rename a column in the same release that stops using it.
- `CREATE INDEX CONCURRENTLY` for large tables (in its own non-transactional migration).
- Migrations run as a separate release step (`crm_migrator`) before new app instances start, never on app boot.
- Every migration is tested against a production-sized anonymised snapshot before Phase 5+ releases.

## 12. Backups and restore

- Managed PostgreSQL with continuous WAL archiving / PITR. Pilot recovery window: 7 days, subject to the provider's PITR capability. **RPO is not assumed from the retention window**: it is measured in the restore drill (time between the last committed test write and the latest recoverable point) and documented with its limitations (target ≤ 15 min, NFR-021).
- Daily snapshot retained 35 days. A monthly logical dump (`pg_dump -Fc`) is copied to a separate account/bucket with object lock, retained 12 months.
- Quarterly restore drill to a scratch instance: verify row counts and a checksum query, run smoke tests, record the RTO achieved.
- Object storage: versioning + lifecycle rules. Bucket replication to a second region is a Should at base workload.

## 13. Partitioning and archiving (deferred)

Candidates: `lead_activity`, `audit_log`, `communication_event`, `interaction`, `import_row`. Partition by month on `occurred_at` when a table passes ~100M rows or vacuum/index maintenance becomes a problem. Partitioning does not change the application interfaces.
