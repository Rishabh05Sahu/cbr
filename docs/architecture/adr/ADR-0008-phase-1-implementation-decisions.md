# ADR-0008: Phase 1 implementation decisions

- **Status:** Proposed. Reported to the business owner in [PHASE-1-REPORT.md](../../PHASE-1-REPORT.md).
- **Date:** 2026-10-20

## Context
Building the Phase 1 foundations surfaced decisions that refine, or deviate from, the Phase 0 blueprint and ADR-0003/0004. The owner asked for trade-offs to be explained before any architectural deviation. Each item below lists the decision, why, the alternative, and how it is enforced or tested.

## Decisions

| # | Decision | Why | Alternative considered | Enforcement / evidence |
|---|---|---|---|---|
| 1 | **Org-administration HTTP endpoints of the auth library are disabled.** Invite, cancel invitation, role change, member removal, member/invitation listings, full-org fetch, org create/update/delete, user update/delete and email change are disabled. These mutations run only through our Server Actions, which call the library's server API. | One path per mutation, with **our** `authorize()`, our rate limits (D3) and our audit. The library's HTTP endpoints would bypass all three | Keep the endpoints and add library hooks for audit/authz. Rejected: the hooks do not receive the acting user | `DISABLED_PATHS` in `src/platform/auth/auth.ts`; e2e asserts 404 for 13 endpoints |
| 2 | **Closed sign-up** via the library's `user.validateUserInfo` gate. Public email/password sign-up needs a pending, unexpired invitation for that address. Platform owner provisioning writes the user row through the `crm_auth` connection (server-only code) | Pilot has no self-service sign-up (OD-16). An earlier AsyncLocalStorage "provisioning" flag **leaked through pooled connections** and reopened sign-up; it was removed | ALS flag (rejected, unsafe); a custom sign-up endpoint | Integration + e2e: sign-up without invitation creates no account. The library's response is deliberately indistinguishable (no enumeration) |
| 3 | **Origin/CSRF checks forced on** (`advanced.disableOriginCheck: false`, `disableCSRFCheck: false`) | The library silently disables them when `NODE_ENV=test` or `TEST` is truthy. A stray env var in production would remove CSRF protection | Rely on defaults (rejected) | e2e: cross-origin cookie-bearing request → 403 |
| 4 | **"Remove member" = deactivate** (status `DEACTIVATED`, team spells closed, sessions revoked). Membership rows are never deleted | Domain model: memberships are never deleted; history and audit references stay valid. The library's hard delete would also fail on team-history foreign keys | Library `removeMember` (rejected) | Integration test: row kept, spells ended |
| 5 | **Permission catalog is code** (`src/platform/authz/permissions.ts`); no `Role`/`RolePermission` tables yet. Membership stores one role code (CHECK constraint) | Roles are fixed and immutable in Phase 1. Tables add no value until custom roles (Phase 7) and would need their own tenant isolation. A code matrix is reviewed like code and unit-tested against the approved matrix | Seeded per-org tables (ADR-0004 wording) | Unit test asserts the approved matrix for every Phase 1 permission × role |
| 6 | **Shared rate limiter on Valkey** (atomic Lua INCR+PEXPIRE). Used as Better Auth's `customStorage` **and** by Server Actions | D3 requires limits on invitation creation, lookup and acceptance, whichever path is used. Server-side library calls are not rate-limited by the library | Library DB storage (no limit for server calls) | e2e: sign-in 429 after 10/min; integration: 31st invitation in an hour refused |
| 7 | **Auth emails are queued directly** (BullMQ) from library callbacks, not via the outbox. Completed jobs are deleted immediately; failed jobs after 24 h | The callbacks run outside our tenant transactions; delivery must not depend on a domain event. Keeping single-use links in Valkey only briefly limits exposure | Outbox (needs a tenant transaction that does not exist at that point) | Worker + Mailpit e2e |
| 8 | **Support access is read-only in Phase 1** even for a `WRITE` grant: database-enforced `SET TRANSACTION READ ONLY` plus a read-only permission set | No reviewed write use case exists | Honour WRITE grants (deferred) | Integration + e2e: writes refused |
| 9 | **Platform "open org for support"** records the org on the platform user's own session row (via `crm_auth`). Access still needs an approved, unexpired grant, checked on every request | Platform staff have no memberships, so the library's set-active refuses them | A separate support session type (more code, same guarantees) | e2e: no grant → no data; grant → read-only data |
| 10 | **UI primitives are hand-written Tailwind components**; shadcn/ui is deferred | Phase 1 screens are simple settings/admin forms; this avoids adding Radix and related packages now | shadcn/ui (planned; re-evaluate with Phase 3 workspace UI) | — |
| 11 | **One Docker image, three targets** (`web` standalone, `worker` esbuild bundle + production dependencies, `migrate`). Non-root runtime | Same image lineage for web and worker (ADR-0001); migrations as a release step (database-design §11) | Separate repos/images | `docker build` for all targets; web smoke test |
| 12 | **Outbox relay through definer functions** (`app.outbox_claim` with lease + `SKIP LOCKED`, `app.outbox_mark_published`); BullMQ `jobId` = event id | The relay must see pending events across orgs without a privileged runtime role | Run the relay as `crm_migrator` (rejected: owner role at runtime) | Integration: published once, re-enqueue deduplicated, handler skips org mismatch |
| 13 | **Mandatory authenticator-app 2FA for Owners, Admins and platform staff** (owner decision item D, 2026-10-20). Request-context resolution returns `TWO_FACTOR_REQUIRED` for these roles until an authenticator is enrolled. Pages redirect to `/app/security/two-factor`; Server Actions and the platform console refuse. Owners/Admins/platform staff cannot turn 2FA off (`/two-factor/disable` → 403) and can only replace the authenticator | Owners and Admins can export and change customer data; a password alone is not enough before real data | Enforce per org via a policy setting (deferred; the requirement is role-based and global for the pilot) | Integration `two-factor.test.ts` (20); e2e `two-factor.test.ts` (7); mutation: removing the guard fails 3 tests |
| 14 | **Recovery codes stored as keyed hashes** (HMAC-SHA-256, HKDF-derived key) through the library's `storeBackupCodes` hook. A before-hook hashes the submitted code. 10 codes × ≈ 59 bits, normalised for case/spaces/dashes | The library default stores codes reversibly encrypted; a leaked DB plus secret would reveal them | Library default (rejected); our own code table (rejected: duplicates the library's single-use compare-and-swap, lockout and challenge handling) | Integration: only `h1:` hashes stored; single use incl. under concurrency; regenerate invalidates old codes; stored hash rejected as a code. Mutation: plain storage fails 6 tests |
| 15 | **Enrolment ends all older sessions; trusted devices disabled** | A session created with only a password before enrolment must not keep Owner/Admin access; "trust this device" would skip the second factor for 30 days | Keep sessions (rejected) | Integration: pre-enrolment session invalid; `trustDevice: true` sets no trust cookie and the next sign-in still requires 2FA |
| 16 | **Lost authenticator:** self-service replacement needs password + a second factor (current code or recovery code), rate-limited. The **platform-assisted reset** (phone and codes lost) follows the identity checks in the [2FA recovery runbook](../../runbooks/two-factor-recovery.md). It ends sessions, makes the password unusable and forces an email password reset plus re-enrolment, so it grants no access by itself | Avoid a path where knowing the password or controlling the inbox alone bypasses the second factor | Owner-initiated reset of an Admin's 2FA (rejected: a compromised Owner session could strip an Admin's factor) | Integration + e2e for both paths; staff cannot reset themselves |
| 17 | **Security events are audited per org and emailed to the user:** 2FA enabled/disabled, recovery code used (with codes left), codes regenerated, authenticator reset, platform reset | Owners see factor changes of their Admins; users learn of unexpected use | — | Integration and e2e assertions on audit rows and Mailpit |
| 18 | **Managed-database role bootstrap leaves the provider admin with ADMIN-only membership in every `crm_*` role** (PostgreSQL 16+). A non-superuser CREATEROLE admin (`doadmin`, `neondb_owner`) automatically becomes a member of each role it creates, with `ADMIN OPTION` true, `INHERIT` false and `SET` false. The direction is "admin is a member of `crm_*`": the admin can later ALTER, DROP or GRANT those roles, but gains none of their privileges and cannot act as them without first granting itself SET. The `crm_*` roles gain nothing. The only other membership is `crm_definer` ← `crm_migrator` (INHERIT, SET, no ADMIN). Application roles are members of no role | PostgreSQL behaviour (`createrole_self_grant` empty). The bootstrap superuser grants it, so the admin cannot revoke it, and the admin needs it to manage the roles. The admin already has BYPASSRLS, so it adds no new power | Revoke it (not possible as the admin; it would also block role clean-up) | `scripts/db/bootstrap-managed-roles.sql` prints `admin_memberships_left`/`admin_only` = `1\|1`. The managed-run report (`scripts/managed-db/s1-report.mjs`) requires **exactly** these memberships, with this member, direction and flags, and that no `crm_*` role can reach any privileged role. `tests/integration/db-roles.test.ts`: the app roles cannot SET ROLE to, and are not members of, any privileged role found in the catalog, which must include the provider admin |

## Consequences
- (+) Every org-admin mutation has exactly one authorised, rate-limited, audited path, and real-route tests cover it.
- (+) Two auth-library behaviours that would have silently weakened security were found and neutralised (#2, #3).
- (−) 2FA depends on the library's `storeBackupCodes` hook, its endpoint paths and its hook context (the before/after hooks share a per-dispatch context object). The 2FA suites must pass on every Better Auth upgrade.
- (−) Upgrading Better Auth needs the regression suites (`test:integration`, `test:e2e`) to pass, because we depend on its path names, the `validateUserInfo` semantics and the origin-check flags.
