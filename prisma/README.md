# Database schema and migrations

- `schema.prisma`: the Phase 1 foundation schema. It covers identity, organisations, membership, teams, support access, audit and the outbox. Later-phase CRM tables are added by their phases.
- `migrations/0001_foundation`: generated by `prisma migrate diff` from the schema.
- `migrations/0002_security`: **hand-written**. It holds everything Prisma cannot express. Review it together with any schema change.
- `migrations/0003_leads` (Phase 2 M1): lead tables generated by `prisma migrate diff`, followed by a hand-written part (below its marker) with the lead CHECKs, partial unique indexes, RLS and grants.
- `migrations/0004_assignment` (M3), `migrations/0005_imports` (M4) and `migrations/0006_hygiene` (M5): same layout.
- `migrations/0007_lead_email_normalized` and `migrations/0008_lead_name_sort_index` (M6 performance, P-B and P-D): **hand-written** only. Reviewed and applied to `crm_perf` first, then promoted unchanged on 2026-10-26 (SHA-256 `4f26dbdc…` and `d241074b…`) and applied to the local `crm_test` and `crm_dev`. See docs/PHASE-2-M6-LOAD-TEST-PLAN.md §8.1.

Migrations run **only** as `crm_migrator` (`pnpm db:migrate`, or the `migrate` Docker target in a release step), never on app boot. Never edit an applied migration.

## Roles (database-design §2.4)

| Role           | Used by                                                                            | Can                                                                                                                                        | Cannot                                                                                                                                                              |
| -------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `crm_migrator` | release step                                                                       | own the schema, run migrations, maintenance policy                                                                                         | — (never used at runtime)                                                                                                                                           |
| `crm_app`      | web + worker business code via `withTenant()`                                      | tenant rows for `app.org_id` only; own `user` row (name, phone)                                                                            | read credentials/sessions, write memberships/invitations, bypass RLS                                                                                                |
| `crm_auth`     | Better Auth only (D2)                                                              | `user`, `session`, `account`, `verification`, `two_factor`, `organization`, `organization_membership`, `invitation` (cross-org, by design) | any other table (teams, audit, outbox, support grants, CRM data); `SET ROLE`                                                                                        |
| `crm_platform` | platform console                                                                   | organisations (incl. status), platform audit (`org_id IS NULL`), support-grant requests, `app.platform_org_overview()`                     | users, memberships, invitations, teams, outbox, any tenant PII                                                                                                      |
| `crm_definer`  | owner of `SECURITY DEFINER` functions (NOLOGIN)                                    | column-limited reads via `definer_lookup`/`definer_relay` policies                                                                         | log in                                                                                                                                                              |
| `crm_cleanup`  | worker import-file cleanup sweep only (M4; own connection, `CLEANUP_DATABASE_URL`) | connect; `USAGE` on schema `app`; `EXECUTE` on `app.import_files_due`, `app.export_files_due`, `app.export_file_deleted` (M5)              | read or write any table; inherit or `SET ROLE` to anything; bypass RLS (NOINHERIT, no memberships; created by `scripts/db/provision-cleanup-role.sql`, before 0005) |

## Objects that exist only in raw SQL (0007_lead_email_normalized, 0008_lead_name_sort_index)

A future `prisma migrate diff` will propose dropping the generated column. **Reject that change in review.** Prisma cannot express a generated column, so `email_normalized` is deliberately not in the `Lead` model. The application reads it only through raw SQL (`detectEmailDuplicates`, the set-based import prototype).

| Object                                                                                                                                                                            | Purpose                                                                                                                                                                                                                                                                                |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lead.email_normalized` (`TEXT GENERATED ALWAYS AS (lower(email::text)) STORED`) and partial index `lead_org_id_email_normalized_idx` (`org_id, email_normalized` where not null) | Exact, case-insensitive e-mail duplicate check that an index can serve under RLS (citext equality is not LEAKPROOF; text equality is). Not unique: duplicates stay a review queue. No grant: `crm_app` cannot write it (generated), and its column-level UPDATE grant does not list it |
| Index `lead_org_id_full_name_id_idx` (`org_id, full_name, id`)                                                                                                                    | "Name (A–Z)" sort and its keyset pagination. Also declared in `schema.prisma` (`@@index([orgId, fullName, id])`), so Prisma knows it                                                                                                                                                   |

On a populated production table:

- 0007 rewrites the table under ACCESS EXCLUSIVE (3.0–4.8 s for 255k leads on the laptop);
- 0008 should be built with `CREATE INDEX CONCURRENTLY` in its own step.
